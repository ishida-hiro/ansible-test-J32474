# 検証記録様式 記入要領

- **様式**: `docs/06_検証記録様式.xlsx`（**サーバ 1 台につき 1 ファイル**。複製して使う）
- **目的**: 各メンバーの検証結果を同じ物差しで持ち寄り、次の3点を議論できるようにする
  - 手動と Ansible のどちらが効率的か
  - 1 台目と 2 台目で作業量や品質がどう変わるか
  - どこが共通化でき、どこが案件固有か
- **ファイル名**: `検証記録_<記入者>_<ホスト名>_<何台目>.xlsx`（例: `検証記録_石田_TOKYO-SWS-AZ_1台目.xlsx`）

---

## 1. シート構成

議論で持ち寄る項目（構築できた項目／構築できなかった項目／実施手順／工数／課題）に 1 シートずつ対応させています。

| シート | 書くこと | 議論で持ち寄る項目 |
| --- | --- | --- |
| 基本情報 | 記入者・対象サーバ・環境・構築方式と、工数・結果の自動集計 | ― |
| 工数 | 作業ごとの開始・終了時刻、作業時間と待ち時間 | 工数 |
| 設計項目別結果 | 設計書の項目ごとに、構築できたか・どの方法で構築したか | 構築できた項目 / 構築できなかった項目 |
| 差分・修正 | 既存資産から変えた箇所を 1 件 1 行で記録する | （共通化の議論の材料） |
| 実施手順 | 実際にたどった手順 | 実施手順 |
| 課題 | 詰まった点・設計書の不備・改善案 | 課題 |

---

## 2. 工数の記録（シート「工数」）

### 2.1 作業区分

**作業区分は次の 6 つに限ります。** どれに当たるか迷ったら、備考に書いたうえで近い区分を選んでください。

| 作業区分 | 内容（Ansible の場合） | 内容（手動の場合） |
| --- | --- | --- |
| 設計書の読み解き | 設計書を読み、何を設定するか・曖昧な点を洗い出す | 同左 |
| 変数化 | 設計値をインベントリ（`group_vars` / `host_vars`）に書く | 設計値を作業用の一覧（パラメータシート）に整理する |
| コード修正 | 変数だけでは表せない差分のために、ロール・Playbook を修正・追加する | 該当なし（記入しない） |
| 実行 | Playbook を流す | GUI・コマンドで設定する |
| 確認 | 結果を確かめる（`99_verify.yml`、証跡、目視） | 同左（`99_verify.yml` を使ってもよい） |
| 手戻り | 誤り・失敗のやり直し（原因調査、修正、再実行） | 同左 |

**手戻りは、初回の作業と分けて記録します。** 例えば Playbook が失敗して直した場合、初回の実行は「実行」、原因調査から再実行までは「手戻り」にします。手戻りの時間は品質の指標になるため、必ず分けてください。

### 2.2 作業時間と待ち時間

1 行ごとに **作業時間**（人が手を動かしていた時間）と **待ち時間**（Windows Update や Playbook の完了を待っていた時間）を分けて書きます。

- 手動と Ansible の差が最も出るのは作業時間です。待ち時間はどちらでもほぼ同じだけかかります（例: Windows Update）。
- 待っている間に別の作業をした場合も、待ち時間として記録して構いません。

### 2.3 対象外

次の作業は、構築方式によらず共通なので工数に含めません。かかった時間は「基本情報」の備考に書いてください。

- VM・ネットワークの払い出し（Terraform・Portal 作業）
- Ansible 実行サーバの準備
- 自動シャットダウンなど、環境の都合による中断

---

## 3. 設計項目別結果（シート「設計項目別結果」）

設計書のテンプレート（「1.概要」と詳細シート）の項目をあらかじめ並べてあります。
**節番号は設計書ごとに異なることがある**ため、「設計書の節」欄には実際の番号を書いてください（例: P様では 1.15 が「サービス設定」、AA様では「ホスト名の戻し」）。
設計書に無い項目は、結果を「−」にして備考に「設計書に記載なし」と書きます。行が足りなければ追加してください。

### 3.1 結果

| 記号 | 意味 |
| --- | --- |
| ◎ | 構築し、`99_verify.yml` の突合せで**自動判定**まで確認した |
| ○ | 構築し、証跡・目視で確認した |
| △ | 一部のみ構築した、または代替手段で確認した |
| × | 構築できなかった（理由を備考に書く） |
| − | 対象外（設計書に記載なし、クラウド側で決まる、構築の範囲外） |

### 3.2 構築方法

| 構築方法 | 意味 |
| --- | --- |
| 変数のみ | 既存のロールに値を渡すだけで構築できた |
| ロール修正 | 既存のロールの処理を変えた（変数の追加を含む） |
| 新規ロール | 新しいロールを作った |
| 手動 | 手作業で設定した |
| クラウド側 | Azure / AWS / Terraform 側で決まる、または設定する |
| 対象外 | 構築していない |

「変数のみ」の割合が高いほど、既存資産をそのまま流用できたことを意味します。

---

## 4. 差分・修正（シート「差分・修正」）

**既存資産から変えた箇所を 1 件 1 行で記録します。** 手動で構築した場合は記入不要です。

| 区分 | 意味 | 例 |
| --- | --- | --- |
| 変数のみ | インベントリに値を書くだけで済んだ | ドメイン名、ローカルユーザ |
| ロール修正 | 既存のロールの処理を変えた | IPv6 無効化の値を変数化した |
| 新規ロール | 新しいロールを作った | ソフトウェア導入 |
| 設計書要確認 | 設計書の記載が曖昧・矛盾していて決められない | OS 版数の記載が食い違う |

「標準に取り込むか」欄は、その修正を他案件でも使うべきか（共通のロールに入れるか）の判断です。**要 / 不要 / 要検討** のいずれかを入れてください。議論②（標準化方針）の材料になります。

---

## 5. 記入の流れ

1. 作業を始める前に「基本情報」を書く
2. 作業中は「工数」に 1 作業 1 行で書き足す（あとで思い出して書くと時間が不正確になるため、その場で書く）
3. 修正が発生するたびに「差分・修正」に書く
4. 構築後に「設計項目別結果」を埋める
5. 最後に「実施手順」と「課題」をまとめる

「基本情報」の集計欄（作業区分ごとの時間、結果・構築方法ごとの件数）は、他のシートから自動で計算されます。
